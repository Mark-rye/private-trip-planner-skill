# 完整攻略蓝本

以用户提供的完整多国攻略中“总览—每日执行—全程速查—预订—费用—准备”的组织方式为模板。
提炼结构与规划方法，不携带用户的酒店订单、支付金额、日期、联系方式或原网页进公开示例。

## 手机上的阅读顺序

1. 首屏：旅行主题、日期、同行者、路线主题、强度、最紧急待办。
2. 日签：按天切换，另有全程总览；出行日期过期时保持原日期，不显示负数倒计时。
3. 每日顶部：今天怎么走、住哪里、已订什么、最需注意什么。
4. 时间轴：景点、交通、餐饮和休息；关键班次明确日期和当地时区，跨夜到达写次日。
5. 今日亮点：为什么值得去、看什么、选哪个时段；文化历史用可展开短段落。
6. 今日备选：因疲劳、天气、延误删什么，保住哪个核心体验。
7. 全程资料：住宿、餐厅、交通、预算、预订、行李及当地实用信息，单列卡片/折叠区。

首屏和当天关键提醒默认展开。不能把末班车、未订酒店或高强度风险藏进折叠文化介绍。
标题、景点数、住宿夜数和百分比应从明细计算；不同城市/国家分段分别查看地图。

## 每日可复用字段

除 stops / legs 外，每日可选：

- stay：今晚睡哪里、入住退房或“夜车/机上/不住宿”；以实际夜晚日期为准。
- meals：早餐/午餐/晚餐选择、推荐菜、餐费范围、预约或套餐含餐。
- highlights：当天 1–3 个关键体验与推荐理由。
- culture：与当日地点有关的历史/文物短介绍，有来源，不使用无依据的排名与赞誉。
- warnings：影响执行的风险、触发条件和应对；默认展开。
- alternative：自由日互斥选项或减量方案，写适合谁、时间、成本与取舍；互斥方案不相加为全天安排。
- booking_ids：引用全程 bookings 的稳定 ID，展示当天状态，无需重复抄金额。

stay / meals / highlights / culture / warnings 为字符串或字符串列表。

## 详细版：模块、样例与内容深度

用户要求全模块详细版时，下表是最低覆盖范围；示例有更多子模块则追加，不能压缩为表中标题。

| 模块 | 必须写到可用的内容 | 示例驱动的验收方式 |
| --- | --- | --- |
| 首屏 | 主题、完整日期、人数、路线、夜数口径、强度、最急待办 | 数字能回查明细，历史日期不显示负倒计时 |
| 路线总览 | 全程据点、按国家／区域分段、绕行取舍、关键转场、图例、比例尺 | 全程与分区地图分别可读，地图注明直线距离 |
| 行程速览 | 每一天的日期、路线、里程／时长、主体验、过夜方式、强度 | 完整天数；手机每行转成一张卡，不截列 |
| 景区亮点 | 每个核心景区的看点、价值、适合时段、停留、体力、预约与当天关联 | 覆盖示例全部景区样例，不只列名称 |
| 每日详细行程 | 起止位置、时间轴、交通接驳、主景区与支线、三餐、休息、住宿、预约条、风险、减量方案、当日文化 | 每个原文日期都有完整正文，新增建议与原文区分 |
| 住宿速查 | 城市／片区、酒店或候选、入住退房和实际夜晚、含餐、接驳、价位、预订／付款状态 | 酒店、夜车、机上分开；未查库存的酒店是候选 |
| 餐厅推荐 | 当地必尝菜、常规选择、高端体验、逐目的地候选、推荐菜、路线适配、价位、订位方式 | 示例逐目的地餐厅组、高端组、菜品组分别覆盖；无依据的评分省略 |
| 交通与包车 | 每段起终点、方式、距离时长、上下车点、行李、预约、费用、备选；包车与混合交通取舍 | 不只写“建议包车”，要能说明哪一段为何用车 |
| 总费用预估 | 交通、住宿、门票、活动、餐食、证件、预留；双人／人均、币种、汇率时间、范围 | 同一当前明细计算；老版不一致时明确作为历史对照 |
| 预订状态看板 | 更新日期、已订／待订／可选／取消、付款、截止日、渠道、优先级、金额、套餐覆盖、待办风险 | 项数完成度与金额占比分开，原文已锁不视为已付 |
| 预算费用报告 | 分类金额与占比、明细、贵在哪里、分地区／每日比较、修订原因、节省方案、结算凭证清单 | 不复抄一个总额，说明结构和如何调整；缺价时仅称小计 |
| 实用攻略汇总 | 证件、网络与离线资料、当地规则、天气／光线与摄影、装备、健康体力、安全、官方紧急联系、失约替代 | 每项写操作和适用条件；法规、电话、签证必须重新核验 |
| 来源与更新 | 原稿、当前核验来源与日期、估算依据、冲突及待确认事项 | 原稿记录只能证明作者当时这样写，不能提升为当前核实 |

每天的执行段落应解释“怎么做、为何如此、延误怎么改”，而非重复景点名。长途转场日也要写行李、餐食、候车、落地与入住；自由日写互斥完整方案，返程日写离境衔接。不能给正文设置少量字数上限而截断示例模块。

写作前建立 `模块 → 子模块／样例 → 原文位置 → 输出位置 → 保留／扩写／待核验` 清单；写作后按原文逐项检查。只覆盖栏目、遗漏餐厅样例或每日历史栏的产物不算详细版完成。用户原稿存在冲突时完整保留对照并新增显式建议，不直接改写其历史订单。

## 结构化详细模块与原稿适配

新写完整行程时，设置 `detail_level: complete`，并提供 `guide_sections`：对象数组，每项含 `id`、`title`、`paragraphs`（字符串列表）、`cards`（可选对象数组，卡片含 `title` 与 `paragraphs`）。固定 ID 为 `route`、`overview`、`highlights`、`accommodation`、`restaurants`、`transport`、`cost_estimate`、`booking_dashboard`、`budget_report`、`practical`、`sources`。每日正文在 `days`，不能只塞到这些概述模块。所有费用引用当前 bookings；非当前原稿数字标注“历史对照”，不冒充自动汇总。

`complete` 模式校验全模块及每日 stay / meals / highlights / culture / warnings / alternative。技术演示数据不启用这个模式，不得作为详细版交付。阅读页会把完整模块的正文和卡片实际渲染出来，而不是只写进数据文件。

`render_reference.py` 的补充 JSON 含 title、disclosure（原稿日期和核验边界）、conflicts（全程冲突）、days（每项 day / advice 字符串列表 / warning）、map（每项 name / lat / lng / region / days / day）。map.region 使用“埃及／约旦”等区域名；地图区域标签从数据推导。脚本保持原正文字节，补充建议独立显示；仅调整可执行显示并阻止原页面外部资源，不把私人正文打包入公开资产。

## 预订与费用

全程 bookings 每项记录 id、name、status、day、日期、付款说明、人数/人均或合计口径，
可选 priority、deadline、note、amount、currency、exchange_rate、included_in。
status 使用 booked（已订）、pending（待订）、optional（可选）、cancelled（已取消）；
paid 为独立布尔字段，只有用户或凭证确认付款时才填 true。

base_currency 为预算展示币种，默认 CNY；travelers 为总人数。
amount 是该项同行者合计金额，不是人均；exchange_rate 是原币 1 单位可换多少展示币。
币种相同时无需汇率，不同币种汇率须有查询时间/来源或标记为用户估算。
缺价项目单独提示，“已知金额小计”不能写成完整旅行总预算。
included_in 引用套餐 ID，该项只展示包含关系、不额外计费；同一套餐只计算一次。
可选事项与已取消事项不计入基础总额。互斥 A/B 方案显示差额或分别预算。
完成度按已订项数计算；付款占比另算，不能把金额占比说成预订完成度。

## 修改后必须交叉检查

- 标题的交通方式是否和详细安排一致；被取消的飞机/大巴是否仍在交通总结或预算。
- 活动结束 + 转场 + 候车缓冲是否早于发车；不足则标注不可行并给出调整。
- 每个自然夜是酒店、夜车还是机上；连住是否覆盖正确日期，夜车与酒店是否重复计算。
- 酒店套餐、门票通票、含餐含车是否重复收费；同一个已订项是否被多个每日卡片重复累加。
- 所有预算、人数口径、汇率、项数、夜数、占比是否来自同一份当前数据。
- 餐厅评分、营业时间、入境规则、演出日与报价是否有当前来源；“用户攻略原文”只证明原文这样写。
- 文化介绍、自由日方案和恢复型体验保留，不因手机排版而只剩景点名称列表。
